# Chancery - Development Guide

## Project Overview
Python/Flask web application for managing an X.509 Certificate Authority (CA).
Handles CA creation, certificate signing/revocation, CSR management, CRL generation, and OCSP responses.

**Renamed from `cert-manager` to Chancery in 2.12.0** (repo, image, UI branding, metric prefix `chancery_*`, `X-Chancery-Signature` webhook header, Basic-Auth realm). Two on-disk identifiers keep the old name on purpose — the default SQLite filename `cert-manager.db` and the SoftHSM token label `cert-manager` — because renaming either would break existing deployments (empty DB / unreachable HSM token). Do not "modernize" them.

## Tech Stack
- Python 3.14, Flask 3.1.3, SQLAlchemy 2.0.52, cryptography 50.0.0
- Bootstrap 5 (CDN), Gunicorn, SQLite

## Project Structure
- `.github/workflows/` - GitHub Actions CI (Docker build & push to GHCR)
- `app/` - Flask application (factory pattern in `__init__.py`)
- `app/models/` - SQLAlchemy models (User — incl. TOTP + session_version columns, CA, Certificate, CSR, AuditLog, MetricsToken, ApiToken, LdapSettings, WebhookSettings)
- `app/services/` - Business logic (crypto_utils, ca_service, cert_service, csr_service, crl_service, ocsp_service, audit_service, auth_service, totp_service (F13), ldap_service, ldap_settings_service, dual_control_service, webhook_service, metrics_service, metrics_token_service, update_service, policy — server-side issuance policy: key strength + validity caps (B4/B5), keybackend/ — base, software, softhsm, pkcs11_session)
- `app/routes/` - Flask blueprints (auth, dashboard, ca, certificates, csr, users, public, health, metrics)
- `app/decorators.py` - `role_required()`, `admin_required` access control decorators
- `app/cli.py` - Flask CLI groups (`keys`, `certs`, `users`, `crl`, `metrics-token`) — see CLI commands below
- `app/templates/` - Jinja2 templates with Bootstrap 5; `_macros.html` holds the shared `expiry_badge`/`status_badge` macros (see Status badges below)
- `tests/` - pytest test suite
- `scripts/seed_demo.sh` / `scripts/seed_demo.py` - demo-data seeder run inside the container (`--reset` recreates, `--remove` deletes only the tagged `Demo …` CAs / `*.demo.example.com` objects **plus whatever a demo CA issued**, since a certificate cannot outlive its CA; a real CA chained under a demo CA is refused unless `--remove --force`)

## Build & Run

### Docker (production)
```bash
./scripts/init-secrets.sh   # generates secrets/master_passphrase, .env (SECRET_KEY, ADMIN_PASSWORD), SoftHSM PINs
docker compose up --build
```
A fresh clone must run `scripts/init-secrets.sh` first — the compose bind-mounts `secrets/master_passphrase` (gitignored) and the app refuses to start with placeholder `SECRET_KEY`/`ADMIN_PASSWORD`. The script is idempotent.

### Pre-built image (GHCR)
```bash
docker pull ghcr.io/guidorugo/chancery:latest
```
Or switch `docker-compose.yml` to use `image:` instead of `build:` (see commented line).

A bare `docker run` (no compose) additionally needs `DATABASE_URL=sqlite:////app/data/cert-manager.db` (the image sets no `DATABASE_URL`; the default relative path resolves under root-owned `/app/instance`, and the uid-1000 process dies with `PermissionError`), `ADMIN_PASSWORD` (the placeholder is refused when seeding the first admin) and `SESSION_COOKIE_SECURE=false` on plain HTTP.

### CLI in the container
`docker compose exec -u app app flask <cmd>` — **always `-u app`**. The container starts as root (only to chown `/app/data`) with `cap_drop: [ALL]`, so root lacks `CAP_DAC_OVERRIDE` and cannot read the 0600 `/run/secrets/*` files; a plain `docker compose exec app flask …` dies with `PermissionError: /run/secrets/master_passphrase`. Every README CLI example uses `-u app` for this reason.

### Local development
```bash
pip install -r requirements.txt
flask --app "app:create_app()" run --debug
```

### Run tests
```bash
pip install pytest
python -m pytest tests/ -v
```

## CI/CD
- **GitHub Actions workflow**: `.github/workflows/docker-publish.yml`
- **Triggers**: PRs → tests only. Push to `master` → tests + image build for validation (**not published**). `v*` tags → tests + build + **publish** (semver tags + `latest`). Publishing is gated to release tags so a merge never auto-pushes an image.
- **Registry**: `ghcr.io/guidorugo/chancery` — uses `GITHUB_TOKEN`, no extra secrets needed.
- **`.dockerignore`**: Excludes `venv/`, `tests/`, `.env`, `.git/`, etc. from the Docker build context.
- **Supply-chain hardening** (findings H2/I1/I2/J1/J2): Actions are **SHA-pinned** (comment = version); base image is **digest-pinned** in the Dockerfile; deps are **hash-locked** (`--require-hashes`); CI runs **pip-audit** (weekly cron too, blocking) and a **Trivy image scan** (report-only, on release tags); release images are **cosign-signed** (keyless OIDC) with **SLSA provenance + SBOM**. Pins are bumped by **Dependabot** (`.github/dependabot.yml`). CI tooling (pytest, pip-audit) is hash-locked too in `requirements-ci.txt`, compiled from `requirements-ci.in` with `-c requirements.txt` (G17-1); the weekly schedule also runs an `image-rescan` job that Trivy-scans the published `:latest` image, report-only (G17-2).
- **Dependencies**: `requirements.in` is the human-edited source; `requirements.txt` is the generated hash-locked lockfile. After editing `requirements.in`, regenerate: `docker run --rm -v "$PWD:/w" -w /w python:3.14-alpine sh -c "pip install pip-tools && pip-compile --generate-hashes --output-file=requirements.txt requirements.in"` (the hash lockfile covers all platforms' wheels, so the regen container's OS doesn't matter). Dependabot (`.github/dependabot.yml`) runs **weekly** for all three ecosystems (github-actions `ci:`, docker `docker:`, pip `deps:` grouped as `python-deps`). The CI `test` job runs on Ubuntu, not Alpine — before merging a dependency bump also run the suite on the pinned base digest (`docker run --rm -v "$PWD:/w" -w /w python:3.14-alpine@<pinned digest> sh -c 'apk add -q build-base libffi-dev softhsm; pip install -q --require-hashes -r requirements.txt; pip install -q pytest; python -m pytest tests/ -q'`), build the image, and boot it once (remember `DATABASE_URL`/`ADMIN_PASSWORD`, see Build & Run).
- **Base image**: `python:3.14-alpine` (digest-pinned; 3.13→3.14 in 2.9.2). Moved off debian-slim in 2.8.0 because trixie carried ~200 unfixable "won't fix" CVEs in Essential packages the app never runs (perl, util-linux, glib2, ncurses — see `IMAGE_VULN_SCAN_12-08-26.md`); the Alpine image scans clean. `pip` is uninstalled from the final image (runtime never installs packages; also clears findings against pip's vendored setuptools/msgpack). Entry scripts are POSIX sh (no bash on Alpine); privilege drop uses `su-exec` (busybox `setpriv` lacks `--reuid`); `softhsm` apk package provides the same `/usr/lib/softhsm/libsofthsm2.so` path; opensc is no longer installed (was diagnostics-only, unused).

## Key Design Decisions
- **Private key encryption**: Fernet + PBKDF2-HMAC-SHA256 (600k iterations). Salt stored with ciphertext.
- **CA certificate re-issue and cross-signing (2.25.0, F11)**: `app/models/ca_certificate.py` (`CaCertificate`, table `ca_certificates`, backref `CertificateAuthority.alternate_certificates`, selectin) holds alternates for a CA's key — `previous` (a superseded primary), `cross` (issued by `issuer_ca_id`, NULL = external/imported), `reissue` (pending dual-control approval) — with `approval_status`/`created_by`/`approved_*`; `is_usable` = approved and, for a cross-cert, issuer not revoked. `certificate_authorities.certificate_pem` stays the primary for every existing reader. `ca_service.reissue_ca_certificate(ca, passphrase, validity_days=, created_by=, approval_status=)` builds a certificate for the SAME key (`_ca_cert_builder`: same subject, BasicConstraints/path_length, CA KU, SKI, Name Constraints, Certificate Policies; AKI from the issuer; new serial; validity clamped to the parent) signed by the parent's backend (or self for a root) and either promotes it at once (`_promote_reissue`: old primary → `previous`, `serial_number`/validity updated, `expiry_notified_at` reset; the route then refreshes the CRL) or stores it as `reissue` pending. `cross_sign_ca(ca, issuer, ...)` refuses self, descendants (loop), unusable/expired issuers, enforces the issuer chain's Name Constraints on the CA's subject, honours the issuer's path-length budget (PKI-6) and validity, and stores a `cross` alternate. `import_alternate_certificate(ca, pem)` attaches an externally issued CA cert whose SPKI matches the key (issuer linked via `_find_parent_by_issuer` when known). `chain_pems(ca, via=)` / `get_ca_chain(ca, via)` / `export_chain_pem` / `export_fullchain_pem(..., via=)` route the chain through a usable alternate at the CA it belongs to (a cross-cert continues from its issuer, or ends when external). Routes (`routes/ca.py`): `POST /ca/<id>/reissue`, `/cross-sign` (`issuer_ca_id`), `/certificates/import`, `/certificates/<alt>/approve` (creator ≠ approver under dual control; approving a `reissue` promotes it), `/certificates/<alt>/delete`; downloads take `via=`; public `GET /public/ca/<id>/alt/<alt_id>.crt` serves approved alternates only. Audit: `reissue_ca_certificate`, `cross_sign_ca`, `import_ca_certificate`, `approve_ca_certificate`, `delete_ca_certificate` (all in the webhook catalog). CA detail has a *CA Certificates* card; `to_dict(detail=True)` lists `alternate_certificates`.
- **Name Constraints (2.22.0, F2)**: `app/services/name_constraints.py`. Stored on `certificate_authorities.name_constraints_json` as `{"permitted": [...], "excluded": [...]}` with the SAN spelling (`DNS:`, `IP:<cidr>` — networks only, `EMAIL:` domain/.domain/mailbox, `URI:` host/.host; no wildcards, no UPN); `CertificateAuthority.name_constraints` / `set_name_constraints`, `to_dict` exposes it. `create_root_ca(..., constraints=)` / `create_intermediate_ca(..., constraints=)` add a **critical** `x509.NameConstraints` (`build_extension`); the create route reads the `nc_permitted` / `nc_excluded` textareas through `normalise()` (ValueError → 400) and audits them; `_import_ca_object` parses an existing extension with `from_certificate` (unsupported GeneralName types are kept as `other:<Type>` for display only). Enforcement (pyca does none at issuance): `enforce(ca, subject_attrs, san_list)` walks the CA and its parents and applies RFC 5280 §4.2.1.10 — for each name type present in a CA's permitted subtrees the name must fall in one (`_dns_within` handles `.sub` prefixes and requires a wildcard to sit wholly inside), any excluded match refuses; requested names = supported SANs + a Common Name that `looks_like_hostname` (two+ labels). Called from `cert_service.create_certificate` (before key generation), `sign_csr` (before claiming), `renew_certificate`, and `create_intermediate_ca` (the sub-CA's own CN against the parent chain). Profiles' `allowed_san_types` and constraints compose. Detail page shows Permitted/Excluded rows.
- **Certificate Policies (2.23.0, F3)**: `app/services/certificate_policies.py`. Stored as `[{"oid", "cps_uri"|null}]` on `certificate_authorities.certificate_policies_json` (set via `create_root_ca(..., policies=)` / `create_intermediate_ca(..., policies=)` from the create form's `certificate_policies` textarea — one `OID [CPS URL]` per line, `parse_entries` validates the OID arcs and requires an http(s) CPS — or parsed from an imported CA with `from_certificate`, which keeps CPS URI qualifiers and drops user notices) and on `certificate_profiles.certificate_policies_json` (profile form/API field `certificate_policies`, exported/imported). The CA certificate carries a non-critical `x509.CertificatePolicies`; `_leaf_builder(..., policies=)` stamps `certificate_policies.for_issuance(ca, profile)` — the profile's list when it has one, else the CA's — on direct issuance, CSR signing and renewal. Intermediates do NOT inherit implicitly; give them their own list. `Certificate.certificate_policies` is parsed from the PEM (shown on the detail page, in `to_dict(detail=True)`); CA `to_dict` exposes `certificate_policies`. `_migrate_schema` now has a `certificate_profiles` block for columns added after 2.13.0.
- **Key algorithms (2.20.0, F5)**: `crypto_utils.KEY_TYPES = (RSA, EC, ED25519, ED448)`; every generation path (CA, certificate, CSR, renewal re-key, both backends) goes through `crypto_utils.generate_key(key_type, key_size)` (runs `policy.enforce_key_strength`; the size is ignored for the Edwards curves), key metadata through `crypto_utils.key_info(key)` (stores `key_size` 256 for Ed25519 / 456 for Ed448 — the column is NOT NULL — and raises for anything else), and the digest for a pyca `sign()` through `crypto_utils.hash_for_key(key)` (None for Ed keys; otherwise per **`SIGNATURE_HASH_POLICY`** (F6, 2.21.0, G5-3): `legacy` (default until 3.0) = SHA-256, `match-curve` = P-256→SHA-256, P-384→SHA-384, P-521→SHA-512 and `RSA_SIGNATURE_HASH` (sha256|sha384|sha512) for RSA — `crypto_utils.signature_hash_name(key_type, key_size)` / `hash_for_key_params` key on the stored columns so the rule also applies while a root self-signs; outside an app context it is legacy). It governs certificates, CRLs, OCSP responses (the CertID digest still mirrors the request) and generated CSRs; existing objects are untouched. `_check_signature_policy` refuses to start on unknown values. SoftHSM: RSA mechanism `SHA{256,384,512}_RSA_PKCS` per digest, EC pre-hashes with the same digest before raw `CKM_ECDSA`, `_sig_alg_name` → `sha{n}_rsa` / `sha{n}_ecdsa`; parity tests per curve in `tests/test_softhsm.py`. `policy.enforce_public_key_strength` is an explicit allow-list (RSA within min/max, the three NIST curves by class, Ed25519, Ed448, else ValueError) and now also runs at `csr_service.import_csr` (G4-3) — a DSA/odd-curve CSR is a 400, never key_type "Unknown". SoftHSM backend: CKK_EC_EDWARDS keys with CKA_EC_PARAMS = the curve OID, raw-message `CKM_EDDSA` signing (the 64/114-byte result is the signatureValue), import via CKA_VALUE (raw scalar), `_sig_alg_name` → `ed25519`/`ed448`; EdDSA is deterministic so certificate/CRL DER is byte-identical to software (parity tests in `tests/test_softhsm.py`). G5-2 done there too: one throwaway key per algorithm per process (`_throwaway_cache`) and both halves of a generated pair carry the SKI as CKA_ID. Forms: key-type dropdowns list Ed25519/Ed448 (size selector disabled, `#ed_note` compatibility text — no browser/Schannel TLS server use); RSA 3072 and P-521 were added to the dropdowns while there. Profiles' `allowed_key_types` accept the new names.
- **Key backends (A1, SoftHSM/PKCS#11)**: A CA's signing key lives behind a `KeyBackend` (`app/services/keybackend/`). Default `software` = today's Fernet-encrypted key; opt-in `softhsm` = key held in a PKCS#11 token, never in Python memory. Selected per-CA (`CertificateAuthority.key_backend`/`key_label` columns); `KEY_BACKEND` sets the default for new CAs, and the create form offers HSM per-CA when `hsm_available()`. Three-state model guards: `has_signing_key` (issue/CRL/OCSP/sub-CA — true for software+HSM), `is_exportable` (key/PKCS#12 export — software only), `signing_capable()` query. pyca can't sign with a PKCS#11 key, so the HSM backend builds the TBS with a same-algorithm throwaway key and swaps in the token's signature via `asn1crypto` (cert/CRL are byte-identical to software for RSA; OCSP is assembled directly since pyca refuses signer≠responder, reusing a throwaway pyca request's CertID). RSA uses `CKM_SHA256_RSA_PKCS`; EC signs the SHA-256 digest with raw `CKM_ECDSA` (SoftHSM lacks `CKM_ECDSA_SHA256`). Cross-backend intermediates work (parent's backend signs the child). Migrate existing keys one-way with `flask keys migrate-to-hsm`; HSM keys are `CKA_EXTRACTABLE=false` so export is refused. **SoftHSM is enabled by default (v2.3.0)**: `docker-compose.yml` wires the PKCS#11 config + the two PIN secrets, `scripts/init-secrets.sh` generates the PINs, and the entrypoint inits the token on first boot — so HSM is offered per-CA out of the box (`KEY_BACKEND` still defaults to `software`, so new CAs stay exportable unless set to `softhsm`). A local `docker-compose.override.yml` is therefore no longer needed. Deployment stays single-container (softhsm2 in the image). Differential tests in `tests/test_softhsm.py` gate byte-parity (skip cleanly without SoftHSM; CI installs it).
- **Master passphrase**: From `MASTER_PASSPHRASE` env var. Used for all key encrypt/decrypt. **Rotation (2.16.0, F18, G13-2)**: `app/services/passphrase_service.py` keeps `ENCRYPTED_COLUMNS`, the registry of every ciphertext column (`certificate_authorities.private_key_enc`, `certificates.private_key_enc`, `ldap_settings.bind_password_enc`, `webhook_settings.secret_enc`); a feature adding a `*_enc` column must register it or `tests/test_passphrase_rotation.py` fails. `rotate(current, new)` checks the current passphrase against one blob per column, re-wraps every blob with a fresh salt (`crypto_utils.rewrap`), verifies each, and flushes without committing — the CLI commits together with its `rotate_passphrase` audit row (or rolls back for `--dry-run`). HSM/cert-only sentinels and NULLs are skipped. The running app keeps the old passphrase in memory (and the OCSP key cache is keyed by ciphertext, so it just misses), hence the documented order: rotate → replace `secrets/master_passphrase` → `docker compose up -d --force-recreate` (bind-mounted secret) → `flask keys check-passphrase`.
- **Delegated OCSP responder (2.24.0, F7)**: with `OCSP_DELEGATED_RESPONDER=true` (default off until 3.0) `ocsp_service.build_ocsp_response` signs with a short-lived responder certificate instead of the CA key: `ensure_responder(ca, passphrase, force=, now=)` has the CA sign a cert (CN `<CA name> OCSP Responder`, KU digitalSignature, EKU OCSPSigning, `OCSPNoCheck`, `OCSP_RESPONDER_VALIDITY_DAYS`=30 bounded by the CA's expiry, same key algorithm as the CA) through the CA's backend (HSM works) and stores it on `certificate_authorities.ocsp_responder_cert_pem` / `ocsp_responder_key_enc` (Fernet, registered in `passphrase_service.ENCRYPTED_COLUMNS`); `responder_status`/`responder_needs_rotation` (missing, invalid, not issued by the current CA cert, or < `OCSP_RESPONDER_RENEW_BEFORE_DAYS`=7 left). An **expired CA** (`ocsp_service.ca_expired`) never gets a responder: `ensure_responder` raises, the hourly job and the CLI skip it (`skipped_expired`), and the request path answers with the CA key (2.24.1). The delegated response is built with pyca (`responder_id(HASH, responder)`, `certificates([responder])`, `sign(responder_key, hash_for_key)`), so the asn1crypto HSM assembly is only used on the direct path; the request path renews lazily (audit `ocsp_responder_rotated`, actor `system`) and falls back to the CA-key path on any failure; the hot-path key cache (`_responder_key_cache`, `OCSP_KEY_CACHE_TTL_SECONDS`) holds the responder key, never the CA key. The response cache key includes the signer (responder serial or `ca-key`). Scheduler job `ocsp_responders` (hourly; inert when the flag is off) rotates due responders (audit `ocsp_responder_rotated`/`ocsp_responder_failed`, actor `scheduler`); CLI `flask ocsp rotate-responders [--ca-id N] [--force]`; route `POST /ca/<id>/ocsp-responder/rotate` (admin, audit trigger `manual`); CA detail shows the mode and responder validity with a *Rotate responder* button; `to_dict(detail=True)` has `ocsp_responder`; metric `chancery_ca_ocsp_responder_expiry_timestamp_seconds{ca_id}`. Flipping the flag changes every CA's responder ID.
- **OCSP**: Built-in responder at `/public/ocsp/<ca_id>` (POST) and the RFC 6960 §A.1 GET form `/public/ocsp/<ca_id>/<url-encoded base64 request>` (2.12.6, G8-2). An unparseable request is answered with an OCSP-level `malformedRequest` at HTTP 200 (`ocsp_service.MalformedOcspRequest` → `malformed_response()`), logged at INFO — never a 500. Certificates include AIA extension.
- **CRL Distribution Points**: Auto-populated in certificates using `{scheme}://{server}/public/crl/{ca_id}.crl`. Added via `crl_dp_url` parameter in `cert_service.create_certificate()` and `cert_service.sign_csr()`. The CRL DP field in the create/sign forms is **editable** — users can override the auto-generated URL per-certificate. When `SERVER_NAME_FOR_OCSP` is at its default `localhost:5000`, the hostname is **auto-detected from `request.host`**. A warning banner appears in Advanced Settings when the detected hostname contains `localhost`.
- **Certificate profiles (2.13.0, F1)**: stored, server-enforced issuance policy (`app/models/certificate_profile.py`, `app/services/profile_service.py`, table `certificate_profiles`, auto-created; built-ins seeded by `profile_service.ensure_builtins()` at startup — Web Server, Client Auth, Email/S-MIME, Code Signing, Custom — editable, never deleted, operator edits survive reseeding). A profile fixes Key Usage / EKU and can bound validity (`max_validity_days`), key type/size (`allowed_key_types`, `min/max_rsa_bits`, `allowed_ec_sizes`), SAN types (`allowed_san_types` dns/ip/email, `require_san`, `cn_in_san`) and opt out of the AIA extension. `custom` = no restriction (legacy behaviour; a request naming no profile resolves to it unless `PROFILES_REQUIRE_SELECTION=true`). Enforcement lives in `cert_service.create_certificate/sign_csr` (`profile=` kwarg → `profile_service.enforce()`), so the API is bound too; for a named profile the posted `ku_*`/`eku_*` fields are ignored. Form/API field `profile=<key|id|name>`; stored on `certificates.profile_id` / `certificate_signing_requests.profile_id` (`to_dict` exposes `profile`). A CSR can carry a *requested* profile (preselected on the sign page; the signer's choice wins and `sign_csr` audits `profile_changed`). Per-CA allow-list `certificate_authorities.allowed_profiles_json` (NULL = any; set at creation or via `POST /ca/<id>/profiles`, audit `update_ca_profiles`). Admin UI: Preferences → Profiles (`/users/profiles[...]`, audit `create_profile`/`update_profile`/`toggle_profile`/`delete_profile`; delete refused for built-ins and referenced profiles). CLI `flask profiles list|export|import <file> [--replace]`. The create/sign forms render the profile list from the DB (`profiles_json`) and lock the KU/EKU checkboxes unless Custom is selected; `MAX_RSA_KEY_SIZE` (default 8192) caps generation and CSR keys (G7-1). Profile CRUD is configuration, not issuance — dual control does not gate it.
- **3.0 UI shell**: `base.html` renders two layouts from one `content` block — the **app shell** for signed-in users (dark left sidebar `aside.app-sidebar` = Bootstrap `offcanvas-lg` so it collapses behind a hamburger below `lg`; grouped nav built by the `nav_item` macro with the active entry derived from `request.blueprint`/`request.endpoint`; sticky top bar `header.app-topbar` with the `{% block topbar %}` page title, the theme toggle and a user dropdown that holds Change Password / Two-factor / API Tokens and the POST logout form; version + update badge in the sidebar footer) and the **auth layout** (`body.auth-body`, centred `.auth-card`, floating theme toggle, footer with the version) for anonymous pages. Pages use the `_macros.html` helpers: `page_header(title, subtitle, id, badges)` as a `{% call %}` block whose body is the actions toolbar, `kv(label)` rows inside `<dl class="kv">` on detail pages, `csr_status_badge`, `empty_row(colspan, text, icon)`, `pem_block(id, text)` (copy button via the shared `data-copy-target` handler in `base.html`). Lists sit in a `.card` + `.table-responsive`, filters in a `.filter-bar`. Icons are **Bootstrap Icons 1.11.3** from jsdelivr (SRI-pinned; the CSP already allows jsdelivr for `style-src`/`font-src`). Badges keep Bootstrap's `bg-*` classes (tests grep `bg-success">Active`) and are restyled to soft pills in `style.css` (`--chy-*` design tokens, indigo accent, both themes). `dashboard.js` is still served (a test asserts it) but only decorates timestamps; the dashboard gets `attention` (expiring certs, pending CSRs, pending CAs), `signing_cas` and `activity` (last audit rows) from the route. Keep the test-coupled strings when touching templates: `>Preferences</a>` in the admin nav, `>Users</a>` tab, `action="/auth/logout"`, `theme-toggle`, `data-bs-theme`, `table-warning` rows and no `bg-light`/`text-muted`.
- **Dark theme**: Bootstrap 5.3 `data-bs-theme`-based. An inline head script applies the saved theme (`localStorage` key `theme`) or the OS `prefers-color-scheme` before first paint; `.theme-toggle` buttons (navbar when logged in, floating top-right otherwise) switch and persist it. Use adaptive utility classes (`bg-body-tertiary`, `text-body-secondary`) in templates — never light-only ones like `bg-light`/`text-muted`.
- **Version & update check**: `app/_version.py` `__version__` is the single source of truth (bump on release; `APP_VERSION` env overrides the displayed value). A context processor renders it as footer small-print. The update check (`UPDATE_CHECK_ENABLED`, **on by default**; set false for an air-gapped CA, `app/services/update_service.py`) fetches the latest GitHub release **server-side, cached (`UPDATE_CHECK_INTERVAL_SECONDS`, default 6h), non-blocking (background refresh), fail-silent**, and shows a footer "Update available" badge when behind — no client-side fetch, so no CSP relaxation needed.
- **CSR signer tracking (2.10.0) & certificate issuer (2.11.0)**: `CertificateSigningRequest.signed_by` (FK users, nullable, `signer` relationship) records who signed; set atomically with `status="approved"` inside `cert_service.sign_csr` (new `signed_by=` kwarg, route passes `current_user.id`). NULL for legacy/rejected CSRs; rejection actor stays audit-log-only. `Certificate.issued_by` (FK users, `issuer_user` relationship, 2.11.0) records who issued the cert — the CSR's signer on the sign path, the creating admin on direct creation (`create_certificate(issued_by=)`); shown as "Issued By" on the cert detail page and in `to_dict()`. - **Renewal and re-key (2.19.0, F9)**: `cert_service.renew_certificate(old, passphrase, *, validity_days=None, rekey=False, revoke_old=False, ocsp_url, crl_dp_url, issued_by, force=False)` issues a successor from the same CA with the old certificate's exact `x509` subject, `san_json`, KU/EKU and `profile_id`, re-running `profile_service.enforce` against the profile *as it is now* (a disabled profile refuses; the default validity is the original window, clamped to the profile max). `rekey=False` reuses the public key — the escrowed `private_key_enc` ciphertext is copied as-is (same passphrase), a CSR-signed certificate's key stays with its owner — after `enforce_public_key_strength` (B5); `rekey=True` needs an escrowed key (CSR lineage → "submit a new CSR"). Column `certificates.renewed_from_id` (self-FK, migrated), relationship `renewed_from` / backref `renewals` (selectin, oldest first), `to_dict` exposes `renewed_from_id` + `superseded_by_id`; `requested_by` carries over so a requester keeps seeing their lineage. Route `GET/POST /certificates/<id>/renew` (admin; `certificates/renew.html`), Renew buttons on the detail page and on list rows without a renewal, `renewal_badge` macro ("Superseded") next to the status badge, detail rows "Renewed From" / "Superseded By". - **CRL freshness & OCSP cache**: generated CRLs stamp `nextUpdate` = now + `CRL_VALIDITY_DAYS` (default 7). **In-app scheduler (2.17.0, F8, closes G4-1)**: `app/services/scheduler_service.py` runs one daemon thread per gunicorn worker (started by `create_app` only when `CHANCERY_RUN_SCHEDULER=1`, which `entrypoint-app.sh` sets on the gunicorn exec line alone — never in the boot-time `create_app()`, CLI runs or tests; `SCHEDULER_ENABLED=false` disables). Every `SCHEDULER_TICK_SECONDS` (60) each thread tries the `scheduler_leases` row (`acquire_lease`: conditional UPDATE, TTL 3 ticks, holder `host:pid:rand`); only the holder runs `JOBS` — `(name, fn, min_interval_seconds)` tuples: `crl_refresh` (every tick) regenerates every signing-capable CA's CRL that is missing or expires within `CRL_REFRESH_BEFORE_DAYS` (2), auditing `crl_refreshed` / `crl_refresh_failed` with actor `scheduler`; **`expiry_events` (daily, F10, 2.18.0)** audits `certificate_expiring` / `ca_expiring` once per unrevoked object inside the `CERT_EXPIRY_WARNING_DAYS` window and `certificate_expired` / `ca_expired` once after `notAfter` — a single `expiry_notified_at` column per table tracks both stages (a value before `notAfter` = only "expiring" sent; after it = "expired" sent too; NULL = never; a renewal (F9) creates a new row and the superseded certificate is skipped). Per-job cadence lives in `scheduler_jobs` (`SchedulerJob`: `last_run_at` = last *successful* run, so a failed job is retried every tick; `tick(force=True)` / `flask scheduler tick --force` ignores intervals and the lease). Job failures are isolated and recorded on the lease row (`last_error`) and on the job row; a tick whose error text differs from the previous tick's audits **`scheduler_error`** (no repeat while the same failure persists — the `chancery_scheduler_job_failed{job}` / `_last_tick_failed` metrics show ongoing state). Belt and braces: the public CRL routes regenerate an expired CRL on download for a CA that can still sign (`public._current_crl`, audit actor `system`) and send `Last-Modified`/`Expires`/`Cache-Control: max-age` from the CRL window (G8-4); `/public/*` has its own rate-limit bucket `PUBLIC_RATE_LIMIT` (600/minute). CLI: `flask scheduler status|tick [--force]`; `flask crl refresh [--all]` still works for manual runs. Metrics: `chancery_scheduler_last_tick_timestamp_seconds`, `_lease_expires_timestamp_seconds`, `_lease_held`, `_last_tick_failed`, `_job_last_run_timestamp_seconds{job}`, `_job_failed{job}`. **System actor** (G10-2): `audit_service.log_action(..., actor="scheduler"|"cli"|"system")` writes a row with that username, no user id and ip `local` outside any request; every CLI mutation now audits through it (`unlock_user`, `crl_refreshed`, `recompute_expiry`, `backfill_issuers`, `migrate_to_hsm*`, `import_profiles`, `rotate_passphrase`). A revoked CA can never regenerate its CRL again, so `revoke_ca` publishes a **final CRL** whose `nextUpdate` = the CA's own `notAfter` (`crl_service.publish_final_crl`, G4-8). The revoke routes call `revoke_certificate`/`revoke_ca` with `commit=False, refresh=False`, commit the state change **together with the audit row**, then run the CRL refresh — a refresh failure comes back as a `warning` field (JSON) / flash instead of a 500 and never loses the audit row (G10-1). OCSP responses are cached per `(ca_id, serial, is_revoked, hash-alg)` for `OCSP_RESPONSE_CACHE_TTL_SECONDS` (default 60, 0 disables) — status is **in the key**, so a revoked cert is never served GOOD from cache.
- **CSP script nonce (TMPL-1)**: a per-request nonce (`g.csp_nonce`, exposed to templates as `csp_nonce`) authorises inline `<script>`; `script-src` has **no `'unsafe-inline'`** (all inline `on*` handlers were moved to `addEventListener`). `style-src` still allows `'unsafe-inline'`. Add `nonce="{{ csp_nonce }}"` to any new inline `<script>`.

## Roles & Access Control
- **admin**: Full access to all routes (CAs, certificates, CSR signing/rejection, user management, audit log).
- **csr_requester**: Can create/upload CSRs and view their own CSRs and certificates. Cannot access CA management, user management, or certificate creation/revocation.
- Routes are protected by `@admin_required` or `@login_required` decorators in `app/decorators.py`.
- Ownership enforced: `csr_requester` can only see CSRs where `created_by == current_user.id` and certificates where `requested_by == current_user.id`.
- Templates conditionally hide admin-only links/buttons using `{% if current_user.is_admin %}`.

## Audit Logging
- `app/services/audit_service.py` provides `log_action(action, target_type, target_id, details)`.
- Does NOT call `db.session.commit()` — caller commits as part of its transaction.
- All sensitive actions are logged: login/logout, CA/certificate/CSR operations, user management.
- Audit log viewable at `/users/audit-log` (admin only, paginated).

## Security Hardening
- **Insecure default rejection**: App refuses to start in non-debug, non-testing mode if `SECRET_KEY` or `MASTER_PASSPHRASE` are set to their insecure defaults (`sys.exit(1)`). `ADMIN_PASSWORD` is checked the same way **only in `_create_default_admin`, when it would actually seed the first admin** — so once an admin exists it is unused and can be removed from `.env`. Startup also **warns** (never refuses) when `SECRET_KEY` is shorter than 32 or `MASTER_PASSPHRASE` shorter than 20 characters (`MIN_RECOMMENDED_*_LEN`, G16-1), and `entrypoint-app.sh` warns for PKCS#11 PIN files shorter than 16 (G5-1).
- **Forced first-login password change**: `_create_default_admin` sets `User.must_change_password` on the seeded admin; a `before_request` guard (in `app/__init__.py`) redirects a flagged **session** user to `/auth/change-password` until they rotate it (Basic Auth + public endpoints exempt; logout reachable). Existing users default to `False`, so upgrades don't force anyone. Self-service change-password (`MIN_PASSWORD_LENGTH`, default 12) is available to any local user via a navbar link. Admin-created and admin-reset passwords (`/users/create`, `/users/<id>/reset-password`) enforce the same `MIN_PASSWORD_LENGTH` and set `must_change_password=True` (2.12.6, G6-2) — an account created that way must log in through the web UI once before Basic Auth is accepted (AUTH-3).
- **TOTP second factor (2.27.0, F13)**: `app/services/totp_service.py` is RFC 6238 on stdlib `hmac`/`struct`/`base64` (SHA-1, 6 digits, 30 s, ±1 step window); `users.totp_secret_enc` is Fernet-wrapped under `MASTER_PASSPHRASE` and registered in `passphrase_service.ENCRYPTED_COLUMNS`; `users.totp_last_step` stores the last accepted step so a captured code cannot be replayed inside its window; `users.recovery_codes_json` holds eight werkzeug-hashed single-use codes (`ABCDE-FGHJK`, no 0/O/1/I). Login: password OK + `totp_enabled` → `session["pre_2fa"]` (user id, 5-minute expiry, method, `next`) → `/auth/2fa` (`auth.two_factor`; code or recovery code; a failure audits `login_2fa_failed` and counts toward the D1 lockout via `auth_service.register_failed_attempt`) → `_finish_login` (`login_user`, `session["sv"]`, `login_success` with `second_factor: totp|recovery`). Enrol at `/auth/2fa/setup` (pending secret in `session["totp_setup_secret"]`, inline SVG QR from `segno` — `qr_svg()` returns None without it — confirm one code, recovery codes rendered once, audit `totp_enabled`); disable = password (local accounts) + code (`totp_disabled`); `/auth/2fa/recovery-codes` regenerates (`recovery_codes_regenerated`). Admin reset: `POST /users/<id>/reset-2fa` (button on the user edit page) and `flask users reset-2fa <username>` (`totp_reset`); both call `routes.auth._clear_totp` and bump the session version. **`REQUIRE_2FA=off|admins|all` (2.28.0; `REQUIRE_2FA_FOR_ADMINS=true` is the 2.27 alias for `admins`)** — `totp_service.enforcement_mode(config)` / `enforced_for(user, config)` are the single source of truth; `_check_require_2fa` refuses unknown values at startup. Enforcement runs through the same `before_request` gate as `must_change_password`, **after** it, so the bootstrap admin's first login is seed password → new password → enrol → app (`_ALLOWED` lists the 2FA endpoints, logout and static). Under enforcement `check_basic_auth` refuses a not-yet-enrolled account with a JSON 403 (after the AUTH-3 gate; bearer API tokens are unaffected), `auth.two_factor_disable` refuses (the setup page hides the form and shows *Required by policy*), and the recovery paths — admin `reset_2fa` route and `flask users reset-2fa` — stay open and say that enrolment is forced again at the next login. Recovery UX: `LOW_RECOVERY_CODES` (2) turns the recovery-login flash red and shows an alert on the setup page; freshly generated codes can be downloaded as a text file (blob URL built by a nonce'd inline script). A TOTP-enabled account is **refused Basic Auth** (JSON 403 pointing at API tokens) in `check_basic_auth`, after the success audit like the AUTH-3 gate; bearer API tokens (F12) still work. LDAP users may enrol too (no password is asked on disable). Webhook events: `login_2fa_failed`, `totp_enabled`, `totp_disabled`, `totp_reset`, `recovery_codes_regenerated`. `TOTP_ISSUER` (default `Chancery`) is the otpauth issuer.
- **Session versioning (G6-4/G6-5, 2.27.0)**: `users.session_version` (default 1) is stamped into the session as `sv` by every login; `load_user` refuses a session whose `sv` differs, so `auth_service.bump_session_version(user, keep_current=False)` logs the user out everywhere — called on self-service password change and every 2FA change (with `keep_current=True`, which re-stamps the acting session), and on admin password reset / 2FA reset (the target's sessions all drop). It also calls `CredentialCache.drop_user(username)` so a cached Basic-Auth credential dies with the old password. Does not commit. Tests: `tests/test_totp.py`.
- **Session cookies**: HttpOnly, SameSite=Lax. `SESSION_COOKIE_SECURE` configurable (default: false, set to true in production).
- **Session timeout**: Configurable via `SESSION_LIFETIME_MINUTES` (default 30).
- **Security headers**: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, a **nonce-based `Content-Security-Policy`** (`script-src` has no `'unsafe-inline'` — see the CSP nonce note above), `Referrer-Policy: no-referrer`, and `Strict-Transport-Security` on all responses.
- **Open redirect protection**: Login `next` parameter validated to reject absolute/external URLs. The unauthorized handler passes a path-only `next` (`request.full_path`), so the redirect is actually honoured after login (G6-3).
- **CSRF error handling (2.9.3)**: a `CSRFError` handler in `_setup_error_handlers` replaces Flask-WTF's raw 400. Anonymous (expired session — e.g. clicking Logout after `SESSION_LIFETIME_MINUTES` idle) → flash + redirect to login; authenticated with a stale token → flash + redirect back (same-host referrer only, else dashboard), the action does NOT execute; JSON/Basic-Auth clients still get a JSON 400. Tests in `tests/test_csrf_error.py` (module builds its own CSRF-enabled app; shared fixtures keep `WTF_CSRF_ENABLED=False`).
- **Timing attack mitigation**: Dummy hash computation on failed login for nonexistent users.
- **Login lockout (D1/AUTH-4)**: per-account failed-login counter (`User.failed_login_count`/`locked_until`, committed directly in `auth_service` so it survives the stateless Basic-Auth path and multiple workers). `LOGIN_LOCKOUT_THRESHOLD` (default 5, `0` disables) failures lock a local account for `LOGIN_LOCKOUT_MINUTES` (default 15). The **last active admin is never hard-locked** (DoS-2 — its counter resets instead) so an unauthenticated attacker can't lock everyone out. Cleared by a successful login, by an admin re-activating or resetting the password of the account (both call `auth_service.clear_lockout`), or via `flask users unlock <username>` (break-glass when the locked account is the only admin).
- **SRI**: Bootstrap CDN resources include `integrity` and `crossorigin` attributes.
- **Content-Disposition sanitization** (`app/services/filenames.py`, G8-1): one shared `content_disposition()` — `filename=` is ASCII-only (fallback `ca-<id>` / `certificate-<id>` when the name is mostly non-ASCII) plus an RFC 5987 `filename*` carrying the exact name. gunicorn writes headers as latin-1, so a non-Latin CA name used to 500 every download, including the public CRL.
- **List search, filter and pagination** (`app/services/listing.py`, 2.15.0, F15): the certificate, CSR and CA lists take `q` (substring: CN/serial/SAN for certs, CN/SAN for CSRs, name/CN/serial for CAs), `status` (certs `active|revoked|expiring|expired`; CSRs `pending|approved|rejected`; CAs `active|revoked|expired|pending|cert-only`), `ca_id`, `profile` (key/id), CA-only `type=root|intermediate` and `backend=software|softhsm`, plus `page`/`per_page` (default 50, max 500). Ownership scoping for requesters is applied before any filter. HTML pages always paginate and show a filter bar + `pager()` macro (`_macros.html`); the JSON API keeps the bare array unless `page`/`per_page` is given, then answers `{items, page, per_page, total, pages}`. Unknown filter values are 400 (JSON) / flash + redirect to the plain list (HTML). Dashboard stat cards link into the filtered views.
- **SAN syntax** (`app/services/san.py`, 2.14.0, F4): one parser/encoder for the `TYPE:value` entries the forms and API take — bare hostname or `DNS:`, `IP:` (v4/v6), `EMAIL:`, `URI:` (`UniformResourceIdentifier`), `UPN:` (Microsoft User Principal Name, `OtherName` OID `1.3.6.1.4.1.311.20.2.3` as a UTF8String via asn1crypto). Any other prefix, a bare IPv6 literal, or an empty value raises ValueError → 400 (G4-4; previously issued as a DNS name). `parse_csr` decodes the same five types (`san.extension_to_strings`); directoryName/registeredID/other otherNames are dropped. Profiles' `allowed_san_types` cover all five.
- **Certificate issuance URLs** (`app/services/public_url.py`, G8-3): the AIA/CDP hostname is `SERVER_NAME_FOR_OCSP` or, while at the default, the request Host; `issuance_urls()` refuses a loopback host outside TESTING/debug (400 — the URL would be baked in for life). Templates receive `ocsp_server` from the same helper and inline it with `|tojson` (G12-1).
- **CSR signing is single-flight** (G7-4): `cert_service.sign_csr` atomically flips the CSR `pending → signing` (`_claim_csr`) before building the certificate and releases the claim on failure; a lost claim raises `CsrAlreadyProcessed` → 409. `csr.create`/`csr.sign` map `ValueError` to 400 (G7-2); `path_length` must be ≥ 0, revocation `reason` must be in `REVOCATION_REASONS` (G7-3), and an intermediate needs a parent (G7-5). `csr_service._generate_key` enforces `MIN_RSA_KEY_SIZE` like the other generation paths (G7-1).
- **OCSP URL scheme**: Configurable via `OCSP_URL_SCHEME` (default: `http`, set to `https` in production).
- **Schema migration**: `_migrate_schema()` in `app/__init__.py` handles adding new columns to existing SQLite tables via ALTER TABLE, and creates the unique index `ux_certificate_authorities_serial` (G9-1; `serial_number` is also `unique=True` on the model for fresh databases).
- **CA names (2.27.1)**: unique among **non-revoked** CAs only, so a revoked CA's name can be reused — `CertificateAuthority.__table_args__` declares the partial unique index `ux_certificate_authorities_name_active` (`WHERE is_revoked IS NOT 1`; `create_all` builds it for fresh DBs, `_migrate_schema` adds it `IF NOT EXISTS`), `ca_service.ensure_name_available(name)` raises the friendly ValueError (400) at the top of `create_root_ca` / `create_intermediate_ca` (before any key is generated) and in `_import_ca_object`; the create route maps a raced `IntegrityError` to 409 and its `_err` helper (like the certificate/CSR form helpers) calls `db.session.rollback()` before re-rendering, because a failed flush left the session in `PendingRollbackError` and turned the 4xx into a 500. The original schema had a table-level `UNIQUE(name)`, which SQLite cannot drop, so `_drop_ca_name_unique_constraint()` rebuilds `certificate_authorities` **once** on upgrade (create-copy-drop-rename from the model's DDL, ids and every column kept, referencing tables untouched, FK enforcement off; on failure the old table stays and a warning is logged). Chain-import auto-names (`_unique_ca_name`) still avoid every existing name, revoked or not. Tests: `tests/test_ca_name_reuse.py`.
- **Last-admin guards**: Cannot deactivate or demote the last active admin user.
- **Non-root container (H1)**: `entrypoint.sh` starts as root only to `chown` the bind-mounted `/app/data`, then drops via `su-exec` to the `app` user (**uid 1000**) which runs `entrypoint-app.sh` (token init, migration, gunicorn). Compose adds `no-new-privileges` + `cap_drop: [ALL]` (only `CHOWN`/`SETUID`/`SETGID` added back). uid 1000 must be able to read the Docker secret files (bind-mounted with host ownership).

## Scoped API tokens (2.26.0, F12)
- `app/models/api_token.py` (`ApiToken`, table `api_tokens`, `chy_api_<token_id>_<secret>`, SHA-256 hash at rest, `scopes_json`, required `expires_at` ≤ `API_TOKEN_MAX_DAYS`=365, `revoked`, `last_used_at`; unique name per user) and `app/services/api_token_service.py` (`create`/`revoke` audit `create_api_token`/`revoke_api_token` through `audit_service.log_action`, `verify` refuses expired/revoked/tampered tokens and deactivated owners, throttled `touch`, `required_scope(method, endpoint)`: GET → `read`; `certificates.create|renew`, `csr.create|sign` → `issue`; `certificates.revoke`, `ca.revoke`, `ca.generate_crl` → `revoke`; every other write → `admin`; public/health/metrics/auth/static → none). The request hook in `app/__init__.py` (`_check_api_token`, called from `check_basic_auth` for any `Authorization: Bearer`) sets the same `g.basic_auth_used`/`g.basic_auth_user` as Basic Auth (CSRF bypass, JSON errors, forced-password 403) plus `g.api_token`, audits `api_token_auth_failed` (401) and `api_token_scope_denied` (403 `"lacks the '<scope>' scope"`). Session and Basic-Auth requests are never scope-checked; role checks still apply, so a token never exceeds its owner's role. A `cmt_` metrics token is refused here and an API token is refused at `/metrics` (different prefixes). UI `GET/POST /users/api-tokens` (any logged-in user; admins see everyone's and may revoke any), `POST /users/api-tokens/<id>/revoke`; navbar link *API Tokens* + Preferences tab; CLI `flask api-token create|list|revoke`.

## HTTP Basic Auth
- **Alternative to session auth**: Enables programmatic access via `curl -u user:pass`, scripts, and automation.
- **Stateless**: No session cookie created — each request authenticates independently.
- **CSRF bypass**: CSRF validation is skipped only for requests with **valid** Basic Auth credentials.
- **JSON error responses**: Basic Auth clients receive JSON `{"error": "..."}` for 401/403 instead of HTML redirects.
- **Audit logged**: Both success (`basic_auth_success`) and failure (`basic_auth_failed`) are logged.
- **Config**: `BASIC_AUTH_ENABLED` (default: true), `BASIC_AUTH_REALM` (default: "chancery").
- **HTTPS required in production**: Basic Auth sends credentials Base64-encoded (not encrypted).
- **Usage**: `curl -u admin:password https://host/ca/` or `curl -H "Authorization: Basic $(echo -n user:pass | base64)" https://host/ca/`.

## Environment Variables
- `SECRET_KEY` - Flask secret key
- `MASTER_PASSPHRASE` - Master passphrase for key encryption
- `DATABASE_URL` - SQLAlchemy database URI
- `ADMIN_USERNAME` / `ADMIN_PASSWORD` - Seed the **first** admin only (when no users exist); a change is forced on first login, after which `ADMIN_PASSWORD` is unused and removable from `.env`
- `MIN_PASSWORD_LENGTH` - Minimum length for a new password on the change-password page (default: 12)
- `SERVER_NAME_FOR_OCSP` - Hostname for OCSP/CRL URLs (default: localhost:5000). When at default, auto-detected from `request.host`
- `SESSION_LIFETIME_MINUTES` - Session timeout in minutes (default: 30)
- `RATE_LIMIT_ENABLED` - Per-IP rate limiting (default: **true**; Flask-Limiter is now a pinned dependency). Initialised **before** the Basic-Auth hook so a flood is 429'd before the password-hash/audit write; `/health` is exempt. Set false to disable.
- `RATE_LIMIT_DEFAULT` - Default rate limit when enabled (default: 60/minute)
- `LOGIN_LOCKOUT_THRESHOLD` / `LOGIN_LOCKOUT_MINUTES` - Failed local logins per account before a temporary lock (default 5; 0 disables) and the lock duration in minutes (default 15); see the Login lockout bullet
- `REQUIRE_2FA` - `off` (default) / `admins` / `all`: force enrolment of a TOTP second factor (gate after the password change; Basic Auth refused until enrolled; no self-disable). `REQUIRE_2FA_FOR_ADMINS=true` = `admins` (2.27 alias)
- `TOTP_ISSUER` - Issuer label in authenticator apps (default: `Chancery`)
- `CERT_EXPIRY_WARNING_DAYS` - Days-before-notAfter to flag a cert/CA "expiring soon" (default: 30) — dashboard counts, badges, JSON API, `flask certs expiring`
- `CRL_VALIDITY_DAYS` - nextUpdate window stamped into generated CRLs (default: 7); the in-app scheduler keeps them fresh
- `SCHEDULER_ENABLED` / `SCHEDULER_TICK_SECONDS` / `CRL_REFRESH_BEFORE_DAYS` - Background scheduler (default on, 60 s tick; a CRL is regenerated once it expires within 2 days)
- `PUBLIC_RATE_LIMIT` - Rate-limit bucket for `/public/*` CRL/OCSP endpoints (default: 600/minute)
- `OCSP_DELEGATED_RESPONDER` / `OCSP_RESPONDER_VALIDITY_DAYS` / `OCSP_RESPONDER_RENEW_BEFORE_DAYS` - Delegated OCSP responder certificates (default off / 30 / 7; F7)
- `OCSP_RESPONSE_CACHE_TTL_SECONDS` - Cache signed OCSP responses per (CA, serial, status) this long (default: 60, 0 disables); status is in the key, so a revoked cert is never served GOOD from cache
- `BASIC_AUTH_ENABLED` - Enable HTTP Basic Auth (default: true)
- `BASIC_AUTH_REALM` - Basic Auth realm name (default: chancery)
- `API_TOKEN_MAX_DAYS` - Longest lifetime of a scoped API token (default: 365; F12)
- `BASIC_AUTH_CACHE_TTL_SECONDS` - In-memory cache TTL for verified Basic Auth credentials (default: 60, 0 disables)
- `OCSP_URL_SCHEME` - URL scheme for OCSP AIA URLs in certificates (default: http, use https in production)
- `SESSION_COOKIE_SECURE` - Send session cookie only over HTTPS (default: **true**; the HTTP reference compose overrides to false)
- `TRUSTED_PROXY_COUNT` - Trusted reverse-proxy hop count for ProxyFix (default: 0 = directly exposed; do not trust XFF)
- `MAX_CONTENT_LENGTH_BYTES` - Max request body size (default: 1048576)
- `MAX_CERT_VALIDITY_DAYS` / `MAX_CA_VALIDITY_DAYS` - Issuance validity caps (default: 825 / 7305); certs are also clamped to the issuing CA's expiry

- `SIGNATURE_HASH_POLICY` / `RSA_SIGNATURE_HASH` - Digest for new signatures: `legacy` (default, SHA-256 everywhere) or `match-curve` (SHA-256/384/512 by NIST curve, `RSA_SIGNATURE_HASH` sha256|sha384|sha512 for RSA); unknown values refuse startup (F6)
- `MAX_RSA_KEY_SIZE` - Maximum RSA key size accepted for generation and in CSRs (default: 8192; G7-1)
- `PROFILES_REQUIRE_SELECTION` - Refuse issuance requests that name no certificate profile (default: false → they use the unrestricted `custom` profile)
- `OCSP_KEY_CACHE_TTL_SECONDS` - In-memory TTL for the decrypted CA signing key used by OCSP (default: 300, 0 disables)
- `UPDATE_CHECK_ENABLED` - Footer "Update available" badge vs the latest GitHub release (default: **true**; set false for an air-gapped CA to make no outbound call)
- `UPDATE_CHECK_REPO` / `UPDATE_CHECK_INTERVAL_SECONDS` - Repo to check (default `guidorugo/chancery`) and cache TTL (default 21600 = 6h)

- `METRICS_ENABLED` - Expose the Prometheus `/metrics` endpoint (default: **false**; returns 404 until enabled)
